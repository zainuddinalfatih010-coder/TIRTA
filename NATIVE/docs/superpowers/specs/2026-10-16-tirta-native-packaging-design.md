# TIRTA Native Packaging Design

## Goal
Package the current stable TIRTA web application into share-ready Windows and Android artifacts without changing its domain behavior: a Windows `.exe` and an Android `.apk` that can be sent directly to reviewers and run without depending on the live Cloudflare URL.

## Baseline and Isolation
- Source baseline: commit `6da03f1` from `E:\TIRTA-VISUAL-LIVE-RELEASE-2026-10-14`.
- Production/live Cloudflare deployment is not modified by this work.
- Golden/stable reference directories are not modified.
- Implementation occurs in an isolated worktree at `E:\TIRTA-NATIVE-PACKAGING`.
- Native build tools, SDKs, caches, Gradle data, Electron downloads, and release artifacts must not be stored on drive C.
- Preferred tool/cache roots: `D:\TIRTA-NATIVE-TOOLS`, `D:\TIRTA-NATIVE-CACHE`; final artifacts: `E:\TIRTA-NATIVE-OUTPUT`.

## Packaging Architecture
### Windows
Use Electron as a thin native shell around the same Vite production build. The renderer remains the existing React application. The Electron main process is limited to application-window lifecycle, secure local loading, native save/open integration where browser download behavior is insufficient, and packaging/signing metadata.

### Android
Use Capacitor as a thin Android WebView shell around the same Vite production build. The renderer remains the existing React application. Native plugins are used only where Android WebView behavior differs materially from the browser, primarily file save/share/open and application lifecycle.

## Source Parity
- Native builds must consume the same production UI/domain source as the web application.
- No duplicate calculation engine, recommendation engine, intervention rules, persistence schema, or report renderer is created for native targets.
- Native-only branching is limited to platform capabilities such as file export/import and shell lifecycle.
- The build records the source commit used for each artifact.

## Persistence
TIRTA currently uses IndexedDB through `IndexedDbStorage` and `ProjectRepository`. Both native shells must provide a stable application origin so IndexedDB data survives app restart. Native packaging must not switch to `file://` in a way that creates unstable or per-launch storage origins.

The existing repository contract remains authoritative. The available SQLite abstraction is not activated merely because a native package exists; switching storage engines would be a separate project and is out of scope.

## File Import and Export
TIRTA's existing report and backup generation remains authoritative. Native adapters may replace only the final delivery mechanism of generated bytes.

Required behavior:
- PDF report can be generated and saved/shared.
- HTML report can be generated and saved/shared.
- `.tirta.json` backup can be generated and saved/shared.
- `.tirta.json` backup can be selected and imported.
- Web behavior remains unchanged when running in a normal browser.

On Windows, prefer native save/open dialogs through an Electron preload bridge. On Android, use Capacitor filesystem/share/file-picker capabilities as required by the platform. No native layer may recompute report or project data.

## Offline Behavior
The `.exe` and `.apk` must bundle the application assets and launch without internet access. Cloudflare remains the web distribution target only. Native packages must not load `tirta-c35.pages.dev` as their main application content.

## Security Boundaries
### Electron
- `contextIsolation: true`.
- `nodeIntegration: false` in the renderer.
- No arbitrary remote navigation.
- Only a narrow typed preload API for file open/save and platform metadata.
- Application content loaded from packaged local assets through a stable secure scheme/origin.

### Android
- App content bundled in the APK.
- No unnecessary permissions.
- Internet permission only if an existing feature demonstrably requires it; otherwise native core flow must work offline.
- File permissions use modern Android document/filesystem APIs rather than broad storage access.

## Distribution Outputs
Final output directory: `E:\TIRTA-NATIVE-OUTPUT`.

Required deliverables:
- `TIRTA-Windows.exe` or an equivalently obvious portable Windows executable suitable for direct sharing.
- A Windows installer may additionally be produced if packaging remains deterministic and does not replace the portable deliverable.
- `TIRTA-Android-release.apk`, signed and directly installable on supported Android devices.
- Android signing key/keystore stored locally outside the shared artifact directory and backed up separately; never committed to Git.
- `SHA256SUMS.txt` containing hashes of shareable artifacts.
- `BUILD-INFO.txt` containing source commit, build date, package versions, and artifact filenames.

## Storage Policy
No large native build dependency may intentionally use drive C. Before native builds, configure:
- npm cache outside C when practical for native dependencies;
- Electron cache outside C;
- Android SDK outside C;
- Gradle user home outside C;
- Android build output in the isolated worktree/output path on D/E;
- temporary packaging directories on D/E where tool configuration permits.

If a tool cannot be prevented from writing substantial data to C, stop and resolve that before continuing rather than risking disk exhaustion.

## Verification Gates
### Shared Web Baseline
Before native packaging is accepted:
- `npm run build` passes.
- full unit suite passes with the same canonical outputs as baseline.
- relevant E2E flows pass.
- no native packaging change alters calculation/domain expectations.

### Windows Artifact
Verify on the built executable, not only in development mode:
- cold launch and offline launch;
- project create/open/save;
- persistence after full app close and reopen;
- Studio Persil → Hujan → Intervensi → Bandingkan → Rencana flow;
- saved intervention data survives navigation;
- PDF, HTML, and `.tirta.json` export;
- `.tirta.json` import;
- no uncaught renderer/main-process errors;
- UI does not expose browser chrome or development tooling.

### Android Artifact
Verify on the built APK or an Android runtime/device, not only desktop responsive mode:
- install and cold launch;
- offline launch;
- project create/open/save and persistence after force-close/reopen;
- core workflow through Rencana;
- mobile layout has no blocking overflow or inaccessible primary controls;
- Android back behavior does not silently discard unsaved intervention drafts;
- PDF/backup export and backup import work through native file APIs;
- no uncaught WebView/native bridge errors.

## Regression Principle
If native packaging requires changing a working domain behavior, calculation rule, project schema, recommendation result, or report content, packaging stops and the issue is redesigned at the shell/adapter layer instead. Native fidelity is subordinate to preserving the known-stable TIRTA behavior.

## Out of Scope
- Rewriting TIRTA as a fully native desktop or Android application.
- Changing domain logic or scientific rules.
- Migrating existing web IndexedDB data automatically into SQLite.
- Changing Cloudflare production deployment.
- Adding online accounts, sync, telemetry, ads, or backend services.
- Refactoring unrelated production code.

## Definition of Done
The task is complete only when a reviewer can receive the Windows executable and Android APK as ordinary files, launch/install them directly, complete the core TIRTA workflow, close and reopen the apps without losing saved project data, export/import project/report files successfully, and observe behavior consistent with the stable web build from commit `6da03f1`.
