PDF references below use **physical PDF page numbers**; printed proposal page = PDF page minus five for the main body.

The integrated direction matches the submitted product grammar and scope; it does not yet implement all submitted features. Seven destinations are a justified decomposition of its four conceptual areas, not a new product. “Dasbor teknis” (p.18) describes orientation/information, not a mandate for KPI cards. “Rekomendasi” means inspectable alternatives and user choice, reconciled with explicit rejection of a single unexplained score (pp.12–13). “Memahami aliran” (p.6) is water-volume disposition, not spatial flow simulation. “Dimensi dasar” (pp.15,24) requires support for genuine measured dimensions; it does not authorize deriving metres from a schematic polygon.

No change to validated baseline formula is authorized by this closure.

TIRTA = **Teknologi Integrasi Resapan, Tampungan, dan Air Hujan**. Users: school/educational-building managers, small/medium building owners and community/early planners. One measured school/building parcel is the competition pilot; application supports multiple independent local projects, one parcel/project. The novelty is integration of spatial modelling, narrow image assistance, deterministic events, constrained alternatives and transparent decisions.

Explicit exclusions: regional/city flooding, flood depth/ponding, peak-flow certification, river/DAS/drainage networks, legal/cadastral maps, safety/compliance/Zero Delta Q certificates, guaranteed construction performance, professional hydrologic/hydraulic/geotechnical/construction design, generative AI, autonomous engineering, required IoT/weather/cloud APIs. No inferred GPS, north, scale, slope, elevation, building height or connectivity.

## C-02 — final story and navigation

MODEL PERSIL → TEST RAINFALL → UNDERSTAND BASELINE → DESIGN INTERVENTIONS → APPLY BUDGET/LAND → EVALUATE FEASIBLE ALTERNATIVES → COMPARE → USER SELECTS → TRANSPARENT PRE-PLANNING PACKAGE.

Retain seven freely navigable destinations. No regrouping: each has a distinct editing/decision responsibility. Guidance is optional and context-sensitive; it never locks completed stages or hides later stages. Clicking a missing input navigates to its owning editor and focuses the exact zone/field. One editing source per concept; other screens link to it rather than duplicate independent forms.

| Destination / question | Owns input and primary action | Evidence always visible / advanced disclosure |
|---|---|---|

Baseline/no intervention is a legitimate explicit choice. Feasible dominated manual plans remain selectable with a transparent dominance note; optimizer output proper contains only non-dominated feasible plans. Never fabricate multiple trade-offs if only one exists.

All numerical science starts UNKNOWN. Disabled/not-modelled optional behaviors use a discriminated state, not a missing value coerced to zero. Explicit zero is valid where physically permitted (rain/C/capacity/cost/occupied area/budget); positive area required for parcel/zones and porous treated area. No “free” cost or “unlimited” land inferred. Currency release scope is IDR with no FX conversion. Parameter source may be a user-authored note/method/reference; the application never writes a fictitious survey/source for them.

Boundary failure has stable code, object ID, path, user-facing safe message and repair destination. Distinguish incomplete valid drafts from structurally corrupt records. Draft UNKNOWN records save, calculations needing them do not succeed. A malformed numeric string remains recoverable draft text until the user corrects or explicitly clears it; it cannot silently leave an older result looking current. Baseline validation is scoped to baseline dependencies; an incomplete intervention must not suppress a valid baseline.

Initial engineering limits: 200 zones, 100 vertices/polygon, 30 scenarios, 5,000 parameters; 10 MiB JSON backup without attachments. Display limits before import/creation; reject oversize rather than truncate. These are resource guards, not inferred physical values.

### C-03a — intervention record details

Component `targets` is a nonempty ordered list of unique existing zone IDs, with a user/source-authored connection/applicability note; porous targets have exactly one item. `placement` is null or `{point:{x,y}, footprint:Point[]|null, context:'schematic'}`; neither property drives capacity or measured area. `performanceByScenario` maps scenario ID to a strict family-specific record:

- Storage: `{availableStorage:ParameterRef, reuse:{mode:'off'} | {mode:'capture-then-reuse', demand:ParameterRef}}`.
- Infiltration/rain-garden: `{infiltrationCapacity:ParameterRef}`.
- Permeable: `{additionalInfiltrationCapacity:ParameterRef}` plus component-level `treatedArea:ParameterRef`; occupiedArea references that same area record, avoiding duplicated truths.

All performance refs use m3/event and refer to input capacity/demand, not achieved credit. Each record includes an applicability note/ref covering the event assumption; unresolved entries are explicit UNKNOWN parameters rather than omitted numbers. Stable error codes distinguish missing performance from exceeded resource limits. No conversion from mm/hour or nominal dimensions is implemented in v1.

Manual plan stores exact selected component IDs/revisions, device priority order, target order, optimizationScenarioId, named comparisonScenarioIds, and `reviewedInputFingerprint|null`. Editing a referenced component invalidates this plan's review until user accepts revised definition; historical saved decision snapshots retain their original component data. Component IDs are unique per installed instance; the same instance cannot occur twice in one candidate. Two quantity choices in the same group are mutually exclusive. Sharing a component between option groups is rejected at configuration time rather than silently de-duplicating an installation. Option IDs are opaque, not inferred from displayed names.

Sensitivity overrides are limited to rainfall depth, scientific area/declared measured dimensions, C and supported event capacity/demand refs. They cannot change cost, occupied land, class, geometry, group membership or target identity; those require a new plan/project revision. Validate override applicability to the scenario's selected performance record; an override supplies a new explicit parameter reference, never mutates the base or a different scenario. A measured area derived from dimensions cannot simultaneously be overridden directly; switch to a declared direct-area sensitivity assumption or override its dimensions and recalculate consistently.

## C-04 — Studio authoring contract

Retain the approved dominant SVG spatial surface, object register and selected data bench. Separate rendering from pure geometry validation/commands. Selection is one `zoneId`, synchronized across canvas/register/inspector/contribution clicks. Stable object identity survives class and geometry edits.

Parcel creation: name + schematic rectangle/polygon + independently entered area with source. Optional **measured rectangle** area method takes explicit length and width in metres with evidence and derives A=L×W as SOURCE_DERIVED. Add `m` to supported units. Show both original measurements and equation; accept this only for a user-declared rectangular measured parcel/zone. It never changes drawing coordinates into a calibrated map. Direct area entry is the default empty form, not a numeric default. Nonrectangular area is explicit measured/source/assumption m²; no guessed width/length. Store the chosen area method exclusively to avoid two conflicting editable area truths. Calibration/georeferencing is deferred.

Zones: create rectangle or click/tap polygon, finish with Enter/Finish; Escape cancels preview. Select/move, edit vertex, insert on edge, remove vertex (minimum three), delete, class assignment, name, area/C and provenance. Copy geometry if offered creates new UNKNOWN scientific area/C/class until confirmed, never duplicate counted area silently. Fit, zoom and pan affect camera only. Optional snap/guides use drawing units and are labelled “sketsa”; no metric scale/north.

Geometry: finite points; ≥3 distinct vertices; no repeated interior vertex or self-intersection, zero-length edge or degenerate polygon. Reject self-touch/crossed/nonadjacent collinear overlaps. Boundary touching between zones/parcel is valid; positive-area zone overlap and outside/crossing containment reject. Validate edges in concave parcel, not just vertices. Production drawing coordinates quantized to a documented 0.001 drawing unit; reject shapes <0.01 square drawing unit (UI numerical tolerance, no m² claim). Use robust predicates and golden adversarial cases. Do not auto-repair imported polygons. Sketch gaps may exist because coordinates are schematic, but scientific sum(zone areas)=parcel area under retained tolerance is mandatory for complete baseline; the distinction is visible.

Parcel edits that would exclude zones reject as one transaction with affected zone list. Zone deletion lists dependent intervention targets/plan impacts; explicit confirm deletes zone, invalidates references/results and preserves old saved plan snapshot for historical inspection. It does not silently retarget or delete interventions. Deleted/unknown references block calculation, not project recovery. Undo restores the transaction. Bounded 100-command undo/redo for authoring and input edits, gestures grouped as one command; new command clears redo; history need not survive reload.

Accessible authoring: named zone list and vertex table with numbered points in **drawing coordinates**, add/remove/move controls; arrow and labelled nudge buttons, numeric drawing-coordinate inputs, rectangle creation from drawing coordinates. All primary operations have keyboard and single-tap alternatives to drag; keyboard shortcuts never intercept text input. Invalid preview remains editable with an error and last valid canonical shape unchanged. Focus stays on the problematic vertex/field; deletion returns to next object/list heading.

Underlay: separate reference-layer upload (PNG/JPEG/WebP), opacity, lock, move/scale in drawing space, source note and remove. Session-only by default; explicit **Simpan referensi dalam proyek** attaches a sanitized image ≤5 MiB/16 MP with media type/size/hash, no EXIF. Scale is visual only; persistent refs store transform and attachment ID. Missing attachment warns without blocking science. Classification images are never automatically used as underlays or vice versa.

Layers: material/class, readiness and current baseline contribution; intervention coverage/selected-plan residual only with matching validated results. Contribution is a volume mark, not runoff direction/depth. Keep compact IDs where labels collide, linked register accessible. Intervention placement/ghost footprints are context only; declared area shown separately. User-entered location and target links remain visibly distinct. No hydraulic arrows on the parcel.

Desktop uses approved canvas/register/bench relationships; at narrow widths keep canvas early, object identity visible, data control moves/focuses to bench/sheet. Mobile full essential authoring remains possible through tap/vertex-table alternatives, not just read-only review. Virtual keyboard and safe-area must not cover inputs. No whole-app scaling.

## C-05 — rainfall, baseline and uncertainty

User creates/renames/duplicates/deletes scenarios; rainfall P in mm and provenance are immediately visible. Blank ≠0. Profiles may be offered only with actual local source/version and explicit selection; no network weather required. Editing a scenario shared by plans invalidates their results; deleting it marks a selected plan's evaluation context missing rather than choosing another scenario silently.

For each zone i: `rain_i = A_i × P/1000`, `baseline_i = rain_i × C_i`. Sum separately. C∈[0,1], positive scientific area; sum of areas must match parcel within retained `1e-9 × max(1,parcelArea)` tolerance. Retain current domain formula, golden tests, units/evidence resolution. `nonRunoff = rainTotal − baselineTotal` is **not identified as infiltration**. Zero rain is a valid current zero result with an accessible zero-state chart.

Show rain input → water falling on parcel → baseline runoff → per-zone contribution on a common scale. Clicking an UNKNOWN cause focuses that parameter in Studio; a bad source opens its source field; a deleted target opens intervention target editor. Do not send every error to rainfall. Studio readiness uses the same dependency validator so “ready” cannot disagree with Hujan.

Proposal sensitivity/uncertainty: an explicit **Uji asumsi** disclosure creates named sensitivity cases with parameter overrides, never hidden statistical intervals. User enters each tested C, area or event-capacity value with ASSUMPTION/source and applicability; absent bounds remain UNKNOWN. Rain remains mandatory in each case. Default scenario has no overrides. Area changes must still reconcile parcel/zone totals; changing only one zone area cannot quietly invent uncovered land. Each case stores override ref→new parameter ref; base values are immutable. Two refs mapping to the same parameter cannot conflict. Fixed taxonomy, units and geometry rules still apply. Present baseline rainfall comparison separately from parameter-sensitivity comparisons, label what changed. No probabilities/return periods/robustness score invented from these cases.

Event-capacity applicability is explicit per scenario. A component stores a performance entry for every scenario included in its evaluation; reusing a value across events requires user confirmation that its source/assumption applies to those events. Do not extrapolate capacity with rainfall, infer a duration, or integrate infiltration rates. Adding a scenario leaves component performance entries UNKNOWN until assigned. Baseline can calculate while intervention results for that scenario remain unavailable.

## C-06 — four intervention families and exact accounting

Common declarations: name, family, one or more explicitly named source zones (catchment targets), applicability/connection assumption, site allocation, total cost IDR, occupied area m², event performance refs by scenario and optional visual position. Parameters may be USER_INPUT, MEASURED, SOURCE_DERIVED or ASSUMPTION with actual source/method; DEMO only in demo projects. No catalogue engineering defaults. Unknown capacity blocks that candidate's water effect; unknown cost/land blocks feasibility. Unknown options can be saved but must be completed or explicitly excluded from a search.

“Feasible” means satisfies the **entered** numerical/target constraints, not physically safe, constructible or permitted. Suitability/connection claims remain user/source assumptions. Source zone is distinct from installation site: a tank receiving roof runoff may occupy ground space elsewhere. All families validate declared target existence and confirmed class; never auto-assign an intervention based on class. Additional applicability restrictions are explicitly declared by source/user, not guessed from a material icon.

| Family | User declares / event capacity | Occupied area and cost | Credited disposition / visual |
|---|---|---|---|
| Tangki (`storage`) | Event-available storage S, ordered target list; mode `storage-only` or explicit `capture-then-reuse` with event nonpotable demand D | Actual declared installation/maintenance allocation, total installation cost; zero area only if explicitly sourced | Captured Q=min(S,available target runoff). Storage-only: retained Q. Reuse mode: reused=min(D,Q), retained=Q−reused. Tank glyph + target label; no icon-size capacity |
| Sumur / area resapan (`infiltration`) | Explicit event infiltration capacity K, targets and applicability; no area×rate derivation | Declared occupied installation area and full cost | Infiltrated min(K,remaining target runoff); resapan glyph/context footprint |
| Rain garden (`rain-garden`) | Explicit event infiltration capacity K under validated MVP; target relation | Garden installation area and full cost; dimensions cannot create performance | Infiltrated min(K,remaining target runoff). Temporary pond/storage is not additionally credited; labelled planting footprint, no simulated water level |
| Permukaan berpori (`permeable`) | Single existing non-porous target zone, explicit treated area T and **additional event infiltration capacity K attributable to treatment**, source/applicability | Occupied area exactly T, consuming the project's usable intervention area once; total replacement/treatment cost | Local additional infiltration min(K, baseline runoff attributable to T). Hatched treatment annotation; existing baseline class/C unchanged |

Tank convention is deliberately a **single capture batch, then within-event reuse**, no refill/turnover credit. S is available space for this event, not nominal tank size. D does not increase Q. Stored water earmarked for later reuse remains retained in this event; a note may explain future intent but adds no reused volume. There is no drinking-water suitability claim. If user cannot support within-event timing, choose storage-only and disclose that choice; no hidden demand default. Reuse enabled with unknown D invalidates its result. This closes the proposal's utilization feature with a transparent conservative assumption instead of fabricating a time-series model.

### C-06a — porous treatment, overlap and partial area

Treatment represents replacing/treating part or all of an existing zone. Require `0 < T <= A_target`, target class ≠porous and ≠null, explicit surface suitability and capacity source. K means incremental infiltration of the baseline runoff attributable to the treated share, not total rainfall infiltration or coefficient reduction. If only a proposed C or total infiltration value is known, it cannot be silently converted to K; user needs a supported incremental event assumption/source, otherwise UNKNOWN.

Uniform baseline C across that existing zone implies its attributable runoff `L = baseline_target × T/A_target`. This proportional allocation is explicit in Catatan Asumsi; split heterogeneous zones in Studio instead of pretending uniform data is measured. Credit `H=min(K,L)` to infiltration, retain the original baseline as comparator and subtract H once from the target ledger. Baseline C and class remain fixed. No additional “avoided runoff” bucket and no simultaneous lower-C treatment baseline.

One selected porous treatment variant per target zone in a candidate. Different sizes of treatment on the same zone are mutually exclusive options, not additive overlapping objects. For multiple disjoint treatments, first split the baseline zone into distinct validated zones with areas/provenance; do not infer treatment subdivision from drawn icon overlap. T counts fully as occupied intervention area, even though it is replacement on existing land; UI calls it “Lahan yang dialokasikan untuk intervensi”, not newly purchased land. Treatment plus another installation cannot claim the same allocation twice: see site ledger below.

Visual hatch indicates **where treatment is proposed**, not measured coverage; annotate “T m² dinyatakan · footprint skematis”. Target geometry alone cannot certify treatment area or disjointness. Existing porous baseline zones are excluded from this family in v1; redesign/upgrade of already porous surfaces is outside this model, not free extra infiltration.

### C-06b — deterministic water and land ledgers

Evaluation convention `event-ledger-v1`, visible in composer: **local porous treatment first; then declared capture/infiltration component order; targets consumed in their declared order**. Porous treatment occurs at the source before remaining water is allocated to other devices. Remaining component order is explicitly reviewed/saved in the plan; changing it creates a new plan revision, can change dispositions, and invalidates results. Optimizer uses this declared priority, does not search hidden permutations. No inferred pipe network or recirculation.

Initialize each zone ledger `R_i=baseline_i`. Apply one porous variant per eligible zone using C-06a, subtract its credit. For each other selected component, compute its event handling limit (S for tank, K for infiltration/garden). Visit target IDs in declared order, take `min(R_i,unused component limit)`, debit R_i and reduce remaining limit. Sum taken water Q; tank divides Q into retained/reused using C-06, others assign it solely to infiltration. No device can draw from non-targets, non-runoff baseline water, pre-existing stored water or another device's already credited water. Target links are volume-allocation assumptions, not hydraulic simulation.

For all results: `B = stored + reused + infiltrated + residual`, `residual=sum(R_i)`. Each disposition and ledger debit finite/nonnegative. Conservation tolerance `1e-9 × max(1, B)` m³/event; fail internal consistency beyond it, do not patch negative volume by broad clamping. Deterministic fixed summation order; display rounding does not affect constraints/dominance. Per-zone/component ledger and source refs are inspectable.

Land: each component assigned to one explicit InstallationSite. Sum allocations within site <= its declared available area; sum component occupied areas <= global usable area, and global usable area <= parcel scientific area. Installation sites are declared disjoint allocations; include explicit user confirmation of disjointness/applicability and a source note. Optional schematic polygons must not visibly overlap as claims of disjoint sites; reject positive-area overlap when supplied, but passing a sketch check does not certify real boundaries. Co-location/stacking and shared-land discounts are unsupported v1: no hidden subtraction of shared footprints. Capacities/costs never scale from symbol size. Equality at cost/site/global area limits is feasible, compared on raw values.

### C-06c — independent acceptance examples (synthetic test inputs)

These values are tests, never production defaults. One zone A=100 m², P=100 mm, C=1 gives B=10 m³.

- Tank S=6, storage-only: stored6, reused0, infil0, residual4.
- Same S, explicit reuse D=4: stored2, reused4, infil0, residual4. D=20 gives reused6, stored0, residual4; it does not capture20.
- Same zone: porous T=40, K=5 gives H=min(5,4)=4. Then tank S=6, D=2 gives stored4,reused2,infil4,residual0. T consumes40m² once; unchanged baseline10/C1.
- Same zone: tank S=6 then garden K=7 yields stored6,infil4,residual0; reverse declared order yields stored3,infil7,residual0. Both conserve10. Order must be visible and persisted.
- Existing porous zone receiving another porous treatment rejects; T>A rejects; two variants for the same target reject; K unknown produces no successful plan result. P=0 with known inputs gives all zero volumes, while installation costs/area remain unchanged.

## C-07 — finite optimizer, goals and alternatives

Input: validated project revision, declared evaluation scenario, option groups/choice lists, allocation order, constraints, optional explicit scenario feasibility scope. Every quantity/size is an exact declared variant. If “0/1/2 tanks” is offered, each choice must declare its complete instance list, costs, occupied area and performance; app may help copy values only by user confirmation, never silently assume linear cost/performance/land scaling.

Before start, validate required options/constraints, compute Cartesian combination count using safe integer/BigInt arithmetic. UNKNOWN budget/global/site area or enabled candidate definitions -> **input incomplete**, no feasible claim. Offer exclusion of an incomplete option with an explicit revised search-space summary; do not omit it silently. No-option/baseline case is included only through declared none choices and remains a visible comparator even if not in search. Requiring an installation is an explicit min-selection constraint; useful for genuine no-feasible cases with zero budget. Do not call an all-none result a successful intervention recommendation.

Stable option groups/choices sorted by ID using fixed code-point comparison; candidate ID is canonical serialized ordered group-choice pairs (or collision-checked hash with retained canonical key). No random/time/display-index identities. Permuted input record storage order cannot change results. Reject duplicate group/choice IDs; semantically identical complete candidate definitions including order/targets/provenance are evaluated once with alias counts. Equal objective triples with different compositions are **all retained**: equality is not dominance. Duplicate removal never hides distinct provenance or composition.

Evaluate with C-06 and raw cost/area/eligibility constraints. Invalid inputs block the requested search before enumeration; infeasible valid combinations are evaluated/rejected with reasons. Record `declaredCombinations`, `duplicateAliases`, `uniqueEvaluated`, `infeasible`, `feasible`, `nonDominated`; equations: declared=duplicateAliases+uniqueEvaluated, uniqueEvaluated=infeasible+feasible, nonDominated<=feasible. Counts shown only from a finished real run. Cancellation preserves inputs, labels partial progress, publishes no final/Pareto result from the prefix.

Initial explicit safety guard: 10,000 raw combinations/run, max30 scenarios, checked before evaluation; benchmark at Gate G and adjust only via documented measured engineering change. Never silently take the first10,000. Worker reports actual completed count and supports cancel; count is progress, not a fabricated ETA. A tested deterministic equivalent algorithm may replace simple exhaustive evaluation later without changing this result contract.

Pareto objective triple on the **explicit optimization scenario**: residual runoff, total cost, occupied area, all minimize. A dominates B iff all three <= and at least one < on unrounded values. No weights, ranking score or hidden fourth objective. Evaluate same definitions across other declared scenarios for comparison; no averaging across rainfall. Optional “harus dapat dievaluasi pada semua skenario terpilih” requires valid performance for all named scenarios; no invented residual target. Any extra hard constraint (quantity maximum, excluded pair, required install) appears in search contract and reasons.

Planning goals match proposal without corrupting Pareto: free-text intended use + **Lihat semua trade-off / Fokus biaya / Fokus ruang / Fokus limpasan**. These are transparent stable sorts over the same non-dominated set, ascending selected objective then stable ID. Labels state sort direction/scenario. They never change feasibility, dominance or selected plan. No crown/recommended emphasis on first row. Explicit view filters show hidden-count/reset action, preserve full set; pagination is presentation only.

Each alternative communicates composition, cost, occupied area, residual, current scenario and source/assumption indicator at equal salience. Compare/choose are labelled actions. No-feasible state shows binding constraints and nearest violations without presenting them as feasible; changes require user input, never automatically relax budget. Dominated/rejected rows remain inspectable in a separate explanation view.

## C-08 — comparison and Rencana & Dampak

Compare uses baseline plus user shortlist (up to six at once, saved shortlist may be larger) and multiple explicit rainfall scenarios. Keep same plan definition, source targets, per-scenario supported performance. Common zero-based volume maximum across currently compared plans/scenarios; declare any scale changes. Cost and area independent of rain remain visually aligned. Missing cells show cause/link, never zero. Display differences numerically/textually as well as bars. Robustness means scenario sensitivity only, not probability of success or safety. Do not mix results with different input revisions or silently compare different assumptions as rainfall-only effects.

Rencana & Dampak is one decision package with the chosen parcel/plan, not four KPI cards. Required fields: user-selected plan name/revision, origin and decision note, parcel miniature and components/targets, active scenario/depth/source, `baseline=stored+reused+infiltrated+residual`, cost/budget/margin, occupied/usable area/margin, per-scenario results, applicability and validity, sources/assumptions/UNKNOWN and limitations. Include explicit “Dipilih oleh pengguna” and pre-planning statement. A retained/reuse label cannot imply safe drinking water.

No selected plan -> explain and link to manual alternatives. Changed science marks package stale immediately; recalculate, then ask user to reaffirm the decision if its evaluation context/meaning changed. Existing selection is preserved as “perlu ditinjau”, not silently switched. Infeasible selected plan remains inspectable with violations, but is not exportable as a current chosen feasible decision; allow a clearly watermarked **draft** report with UNKNOWN/warnings. No stale numeric output appears as current.

## C-09 — result currency and scientific identity

Every result fingerprint includes engine version, relevant canonical numerical values/units/evidence/source/applicability, surface/target identity, scenario overrides, component versions/allocation order and constraints where relevant. Baseline fingerprint excludes unrelated intervention inputs. Cosmetic sketch moves/name changes do not change arithmetic; package revision still updates its presentation identity. Source/class changes invalidate validation even if arithmetic numbers happen to match.

Commit valid edit -> synchronously invalidate dependent result; request recalculation explicitly or auto-recompute inexpensive baseline after commit; never reuse old success while editing an invalid/blank input. Optimizer always explicit run with worker request token. Result accepted only for exact current fingerprint; old worker results discarded. Load/import recomputes from inputs, ignores cached results. Save decision definition plus review fingerprint; no guarantee of future feasibility from a saved selection.

## C-10 — local persistence, migration and offline

Choose **IndexedDB on web, native SQLite on Capacitor Android**, behind one transactional ProjectRepository API: list/read/create/save(expectedRevision)/duplicate/delete/import/export. IndexedDB is not promoted to a reliable native database by wrapping it. Use native preferences only for small UI preferences.
